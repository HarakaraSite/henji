# AI ファースト CLI 設計指針 — henji 開発と実測から得た教訓

作成日: 2026-07-04  
改訂: 2026-07-04 v2（§2 コンテキストウィンドウの経済、§7 回復可能性を設計目標に、を追加）  
出典: henji（charmbracelet/mods フォーク）の開発（PR#1〜#26 + v0.9.3 作業）と、
クリーンルーム環境での3モデル実測（[[model-eval-results-2026-07]]、Opus 4.8 / Sonnet 5 /
Haiku 4.5 が `-h` と `docs` のみで全12タスクを完遂）。

対象は CLI アプリケーション。GUI にはほぼ適用できない（AI が操作面を「読んで」「試して」
「失敗から回復する」ループは、テキスト入出力と終了コードがあって初めて成立する）。
なお多くの項目は AI 専用ではなく CLI 設計の一般論としても通用する — AI は「最も余裕のない
ユーザー」であり、AI に耐える設計は人間にも快適になる。

---

## 0. 大前提: AI は「初見で・独力で・非対話に」使う

人間のユーザーと違い、AI エージェントは:

- **初見**で使う。チュートリアルを事前に読んでいないし、過去の使用経験の記憶も
  当てにならない（古いバージョンの知識で間違ったフラグを推測する）
- **独力**で使う。詰まっても隣の人に聞けない。頼れるのはツール自身の出力だけ
- **非対話**で使う。TTY なし・stdin はパイプ・確認プロンプトには答えられない

この3条件を満たすように設計すると、結果的に人間にとっても使いやすくなる。
逆は成り立たない（人間向けに親切な対話 UI は、AI にとってはハングの原因になる）。

---

## 1. 情報の二層化: `-h` は1行リファレンス、`docs` は全文マニュアル

**指針**: `--help` は各フラグ1行（目安60字）のクイックリファレンスに徹し、
詳細はバイナリ埋め込みの `docs` サブコマンド（プレーン Markdown、設定壊れでも動く）に
委譲する。`--help` のフッターに `Full manual: <tool> docs` のポインタを必ず置く。

**根拠**: 実測で3モデル全員が「まず -h で骨格を掴む → 応用タスクで docs を読む」という
設計どおりの導線を辿った。-h を簡素化（43→29項目、長文説明を docs へ移動）した後でも
不足の訴えは「特定の挙動の一言が欲しい」レベルに収まった。
docs は環境非依存にする — henji では設定ファイルや会話DBが壊れていても `docs` だけは
動くよう、main() で他の初期化より前に分岐させた。

**注意**: -h と docs の乖離はバグとして扱う。henji では `TestManualLongFlagsExist`
（docs 内の `--flag` 参照が実在するかを CI で検証）で機械的に担保している。

## 2. docs にはサイズ予算を設ける — コンテキストウィンドウの経済

**指針**: docs は「エージェントのコンテキストウィンドウにタスクと同居する」前提で、
**サイズ予算（バイト/トークン）を先に決めてから書く**。網羅性ではなくタスク指向の
密度を優先する。予算はテストで強制する — ドキュメントには増える一方向の圧力しか
かからないため、上限が無ければ必ず肥大化する。

巨大な docs が与える悪影響:

- **作業領域の圧迫**: 読んだ分だけタスク本体・中間結果に使える文脈が減る
- **毎回のコスト**: エージェントは記憶を持ち越さないので、docs はセッションごとに
  読み直される。サイズはコストとレイテンシに毎回効く
- **非対称な劣化**: 長文からの要点抽出は小さいモデルほど苦手で、docs が太るほど
  弱いモデルから順に脱落する

**根拠**: henji の docs は 12KB 予算で設計し（実体 9.4KB / 183行）、
`TestManualSizeBudget` が上限超過を CI で落とす（エラーメッセージも
"split topics before exceeding" と分割を促す文言にしてある）。実測では3モデルとも
docs を**1回読むだけ**で応用タスク（構造化出力・会話継続）に必要な情報を引き当てた。
最小モデルの Haiku が3つの障害すべてで「docs のどこを見ればよいか」に到達できたのは、
docs が一望できるサイズだったことが大きい。

**書き方のコツ**:

- 階層で逃がす: -h の1行 → docs の1段落 → それ以上の詳細は載せない（載せたくなったら
  何かを削る）。docs に書くのは「何ができるか + 落とし穴 + 典型ループ」で、
  リファレンス全文ではない
- セクション見出しをタスク語彙にする（henji: "Getting machine-readable output" /
  "A typical agent loop"）。エージェントは grep や部分読みもするため、見出しが
  検索キーになる

## 3. Examples はエージェント向けタスクの導線として設計する

**指針**: `--help` の Examples は「人間が微笑む例」ではなく、**AI が組み立てそうな
タスクの最短経路**を載せる。落とし穴があるならタイトル側に一言埋め込む。

**根拠**: henji の Examples 4本は、パイプ要約・JSON エンベロープ + jq・JSON Schema・
MCP を1本ずつカバーするよう設計し、事前に opencode/codex に「--help だけ」でコマンドを
書かせて検証した。その検証で「--max-tool-calls はツールがある前提に見える」という
誤解が見つかり、例のタイトルに「needs mcp-servers configured」を埋め込んだ。
実測では Opus が Examples から「stdout は安全にパイプできる」「--json-schema の使い方」の
当たりを付けている。Examples は読まれる。

## 4. 出力契約を決めて、明文化する

**指針**: 「**stdout には応答（結果データ）だけ。スピナー・進捗・保存通知・エラーは
stderr。ANSI 装飾は TTY 接続時のみ**」という契約を守り、docs に契約として書く。

**根拠**: 実測で Sonnet 5 は stdout/stderr を別ファイルに取って契約を検証してから
成果物を保存した。Opus は docs の契約明文を読んで「要約テキストだけを確実に保存できる」
と裏付けてから実行した。契約が文書化されていると、エージェントは試行錯誤ではなく
確認だけで前に進める。

**併せて**: 終了コードも契約の一部。失敗時は非ゼロ + 機械可読なエラー（後述）を返す。

## 5. 機械可読モードは「バージョン付きエンベロープ」で

**指針**: `--output json` のような機械可読モードを用意し、(1) 1行 JSON、
(2) `version` フィールド付き、(3) 成功も失敗も同じエンベロープ構造、
(4) 後続処理に必要な ID（henji なら `conversation_id`）を含める。
フィールドの削除・改名時のみ version を上げる、という互換ポリシーをコードコメントに残す。

**根拠**: 実測で Sonnet は `--output json` → `jq -r '.content[0].text'` → 
`conversation_id` を `-c` に渡す、という docs 記載のエージェントループをそのまま再現した。
エラー時も `{"version":1,"error":{...}}` + exit 1 なので、スクリプトから分岐できる。

**教訓（改善バックログより）**: テキスト出力にだけ存在する意味情報（henji の
`[local]` エイリアス表記など）は JSON に**意味として**入れる。3モデル全員が
「JSON からローカル/クラウドを機械判別できない」と指摘した（→ `base_url` を追加済み）。

## 6. 構造化出力は段階を用意し、クライアント側検証+リトライを持つ

**指針**: 「ゆるい形式指定」→「エンベロープ」→「スキーマ制約+検証」の段階を用意する。
最上位（henji の `--json-schema`）は、サーバ側の構造化出力機能に投げつつ
**クライアント側でも検証し、失敗したら訂正指示付きでリトライ**する。

**根拠**: 小型ローカルモデル（gemma E2B）は JSON をコードフェンスで包む。この既知の
落とし穴と対策（"raw JSON only, no code fences" をプロンプトに足す）を docs に書いて
おいたところ、実測では Opus が**予防**し、Sonnet と Haiku が**遭遇後に docs を根拠に
回復**した。ツール側のリトライ + docs の落とし穴記述、の二段構えが効く。

**教訓**: リトライが「何をしているか」（訂正指示の内容）も docs に書く。Sonnet は
「なぜ3回とも同じ失敗をしたのか内部動作が見えない」と指摘した。見えない自動機構は
エージェントの原因分析を妨げる。

## 7. エラーメッセージはエージェント API である — 設計目標は「回復可能性」

**指針**: エラーには (1) 何が悪いか、(2) 有効な選択肢の列挙、(3) 次に打つべき
コマンドのヒント、を入れる。エラーメッセージはエラー処理ではなく**リカバリの導線**。

そして最適化すべき指標は**初回成功率ではなく回復可能性**。リトライはエージェントの
標準動作でありコストが低い。数回の失敗は許容範囲 — 失敗から確実に立ち直れる短い
エラー + 引き当てられる docs の組み合わせは、初回で完璧に導こうとする長い説明よりも
総合的に効く（説明を長くすると §2 のコンテキスト予算を食う。トレードオフの解消先は
エラーメッセージ側）。ただし回復ループには上限を設ける（henji の
`--json-schema-retries` のように回数を設定可能にする）。

**根拠**: 実測で3モデル全員が同じ場所（`-m 5.5` 単独指定）で失敗したが、エラーが
有効な選択肢を列挙していたため全員1〜2手で自力回復した。フラグを捏造したモデルは
ゼロ — 良いエラーは幻覚を抑制する。最小モデルの Haiku は3回つまずいたが**3回とも
回復して完遂**した（事前予想は「Haiku は完遂できないのでは」だった）。この結果は
エラー改善にも反映済み: モデルが別 API に属する場合は
`Try: -a openai -m gpt-5.5 (found in another configured API)` を提示する。

**反例（henji で踏んだ失敗）**: Google API エラーが二重 nil パニックで**すべて**
クラッシュになっていた（PR#19）。パニックはエラーメッセージと違い回復の足がかりが
無い。エラーパスは「正しく失敗する」経路としてプロバイダごとに実 API で検証が要る。

## 8. 暗黙に何かを直したり落としたりしない（silent failure の根絶）

**指針**: 入力の切り詰め・設定値の無視・自動フォールバックを**黙って**やらない。
やるなら stderr に一言出すか、docs に明記する。

**根拠（henji で踏んだ実害）**:
- `max-input-chars` 未設定時にプロンプトが**空文字列に切り詰められて送信**されていた
  （エラーなし。空応答で気づく）
- 未指定のサンプリング値が 0 として送信され、ゲートウェイが 422 を返した
- Google プロバイダは明示的な `temp: 0` を omitempty で**黙って脱落**させていた

エージェントは「出力がおかしい」ことからは原因に辿り着きにくい。§7 の回復可能性は
「失敗が見える」ことが前提 — silent failure は回復ループ自体を起動させない。
失敗は早く・大きく・言葉で。

## 9. 「未指定」と「ゼロ値」を型レベルで区別する

**指針**: 設定値は「未指定（送らない/デフォルト）」と「明示的な 0（有効値）」を
区別できる表現にする（ポインタ、-1 センチネル、Optional 型など）。API リクエストを
組む層まで**一貫して**この区別を運ぶ。

**根拠**: henji は config 層を直しても（未指定=-1）、Google プロバイダの
`json:"omitempty"` が値型の 0 を落とす、という**層をまたいだ不整合**を後から発見した
（F-2）。区別は入口だけでなく出口まで貫通させないと意味がない。

## 10. 最小構成で動くことをテストクラスにする

**指針**: 同梱テンプレートの全項目設定ではなく、**ユーザー（や AI）が手書きする
最小設定ファイル**で正しく動くことを回帰テストにする。デフォルト値は
`defaultConfig()` 相当の一箇所に集約する。

**根拠**: henji の実害バグの多く（空文字切り詰め、422、`max-retries: 0` で
フォールバック即死）は「テンプレートには値があるが最小構成では無い」パターンだった。
AI は docs を読んで最小構成を生成する — テンプレート同梱では守れない。

## 11. 状態（会話・セッション）は捕捉可能な ID で扱い、復元挙動を明記する

**指針**: 状態を持つ CLI は、(1) 状態の ID を機械可読出力に含める、(2) ID でも
人間可読な名前でも参照できる、(3) **状態再開時に何が復元されるか**（henji なら
会話継続時に API/モデルが DB から復元される）を docs に明記する。

**根拠**: 実測で継続方式は2ルートに割れた（Opus/Haiku は `-t` 名前方式、Sonnet は
`conversation_id` 方式）— 冗長な導線は異なるエージェントを救う。一方、復元挙動が
未記載だったため、Opus は「継続時は毎回モデル再指定が必要」と**誤解したまま完走**した
（実機検証で復元されることを確認済み）。未記載の正しい挙動は、エージェントに
誤ったメンタルモデルと無駄な回避策を植え付ける。**完走した = 正しく理解した、ではない**。

## 12. 表面積を絞る。フラグ1本はエージェントの分岐1つ

**指針**: 使用頻度の低いフラグは「隠す」のではなく**消す**（設定ファイルに降格するのも
可）。残すものだけを -h に載せる。

**根拠**: henji は --help を 43→29 項目に削減した（`--theme`、`--fanciness`、
プロンプトエコー等を機能ごと削除、`--temp` 等は YAML/env 専用に降格）。エージェントに
とって選択肢の多さは事故率であって豊かさではない。削減後の実測で「足りない」という
訴えは出ていない。表面積の削減は §2 のサイズ予算にもそのまま効く。

## 13. 設定の解決は決定的に。設定内容は列挙可能に

**指針**: 設定ファイルの探索は「env var → OS 別の単一デフォルト」程度の決定的な
2段階にする（存在チェックで挙動が変わる多段フォールバックは避ける）。また
`--list-models` / `--list-roles` のような**設定内容を列挙するコマンド**を用意し、
機械可読モードに対応させる。

**根拠**: henji は xdg ライブラリの最大5段フォールバック（既存ディレクトリの有無で
結果が変わる）を自前の2段階に置き換えた。実測では3モデル全員が最初の数手で
`--list-models` を叩き、環境を自己把握してから本題に入った。列挙コマンドは
エージェントの「偵察フェーズ」の主食になる。

## 14. 非 TTY で全機能が完結すること。stdin の扱いに注意

**指針**: TTY 検出で対話 UI（フォーム・確認プロンプト）と非対話動作を切り替え、
**すべての機能に非 TTY 経路を用意する**。stdin がパイプの場合の読み待ちセマンティクスを
決めておく（EOF まで読む設計なら、それを docs に書く）。

**根拠**: henji は非 TTY だと入力フォームを出さずエラーメッセージで必要な引数を
案内する。開発中、stdin を開いたまま渡すハーネスで `henji --list-models` が
EOF 待ちでハングする事象を踏んだ — エージェント実行環境の stdin 事情は多様で、
「stdin を読むのはどんな時か」が曖昧だと診断困難なハングになる。

## 15. ツール自体の検証も AI で行う（クリーンルーム評価）

**指針**: 「AI が使えるか」はレビューではなく**実測**する。方法:

1. リポジトリ外の隔離ディレクトリに、バイナリ+素材+指示書だけを置く
2. 情報源を「-h・docs・実行結果」に制限し、ソースや README の閲覧を禁止する
3. タスク文には**フラグ名・機能名を書かない**（発見できるか自体が測定対象）
4. 失敗コマンドを含む全試行と、-h/docs をいつ・なぜ読んだかを記録させる
5. 能力の異なる複数モデルで実施する（最弱モデルが完走できれば強い証拠になる。
   実測でも Haiku 4.5 の完遂 — 3回の失敗と3回の回復込み — が最も説得力のある材料に
   なった）
6. 改善提案を報告させ、複数モデルで一致した指摘を優先着手する

**根拠**: この方法で得た指摘は具体的で（「-m 単独指定の失敗例を Examples に」等）、
3モデルの一致箇所がそのまま優先度になった。開発中のドッグフーディング
（実ゲートウェイ e2e、実 API キーでのプロバイダ検証）も同じ思想 — **モックでは
エラーパスの実態が分からない**（Anthropic の temp+top_p 同時指定 400 や Google の
エラー時パニックは実 API でしか見つからなかった）。

## チェックリスト（新規 CLI 開発時）

- [ ] `-h` は各フラグ1行・60字目安。フッターに全文マニュアルへのポインタ
- [ ] `docs`（または同等）サブコマンドはプレーン Markdown・設定壊れでも動く
- [ ] docs のサイズ予算を決め、超過を CI テストで落とす（henji: 12KB）
- [ ] docs の見出しはタスク語彙（grep・部分読みの検索キーになる）
- [ ] docs 内のフラグ参照が実在することを CI で検証
- [ ] Examples は AI タスクの最短経路をカバーし、落とし穴を一言添える
- [ ] 出力契約（stdout=結果のみ / stderr=診断 / ANSI は TTY のみ）を実装し docs に明文化
- [ ] `--output json`: 1行・version 付き・成功/失敗同型・後続処理用 ID 入り
- [ ] エラーは「何が悪い+有効な選択肢+次の一手」。exit code 非ゼロ
- [ ] 最適化指標は初回成功率ではなく回復可能性（リトライ上限は設定可能に）
- [ ] 黙った切り詰め・無視・フォールバックが無いこと
- [ ] 未指定とゼロ値の区別が出口（API リクエスト層）まで貫通していること
- [ ] 最小設定ファイルで動くことの回帰テスト
- [ ] 状態 ID の捕捉手段と、再開時の復元挙動の明記
- [ ] フラグ棚卸し: 消せるものは消す
- [ ] 設定解決は決定的 / `--list-*` で列挙可能（JSON 対応）
- [ ] 全機能に非 TTY 経路。stdin 読み待ちのセマンティクスを明記
- [ ] リリース前にクリーンルーム AI 評価（できれば弱いモデルを含む複数で）
