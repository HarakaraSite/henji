# AI向けドキュメント/診断コマンド 設計メモ

作成日: 2026-07-05

## 1. 経緯

`--json-schema`実装（`docs/notes`の他メモ参照）に伴い`--help`を4件の固定Example表示に
改善したが、opencode(GLM-5.2)・codexの2エージェントに「`henji --help`だけを情報源に
タスクをこなすコマンドを書かせる」検証を3〜4回行ったところ、以下が判明した：

- **有効だった対応**: `--json-schema`のGoogle固有制約（`additionalProperties`拒否）、
  `--max-tool-calls`のMCP依存、`--api`と`--model`の組み合わせ必須、をそれぞれ`--help`の
  フラグ説明に追記したところ、複数の独立エージェントがその情報を正しく読み取り、
  設計判断に反映できることを確認した
- **解決しなかった問題**: MCPサーバーが実際に設定されているかどうかは、`--help`が
  どれだけ丁寧に書いても静的テキストでは判定できない（環境依存の不確実性）

## 2. 開発者（ユーザー）の問題提起

1. `--help`の改善には効果があるが限界がある
2. `--help`は人間も読む。AI向けの注記を足し続けると人間のクイックリファレンスとして
   煩雑になる（フラグ1行の説明が既に長くなりつつある）
3. `--ai-description`のような別フラグ/サブコマンドを新設し、`--help`から誘導する方が
   良いのではないか
4. ただし使い方の説明は頻繁に改訂される。Goソース中に文字列としてハードコードするより
   外部ファイルから読む工夫が要るのでは

## 3. Claude（実装担当）の初期意見

1〜3に同意。4については実行時の外部ファイル探索は「見つからない/古い」という新しい
失敗モードを持ち込むため、既に`config_template.yml`で使っている`//go:embed`
（ビルド時にファイルをバイナリへ埋め込む）パターンの流用を提案した。

## 4. Claude Fable 5（henji経由でレビュー依頼）の指摘

henjiを実際に使い（`henji --api anthropic --model fable-5`）、上記の議論をレビューして
もらった。特に重要な指摘を優先度順に記録する。

### 4.1 最重要の見落とし: 静的ドキュメントの限界そのものは`--ai-description`でも解決しない

`--ai-description`は結局のところ**静的テキスト**であり、開発者の問題提起1
（実行時・環境依存の不確実性は静的テキストで解消できない）に対する解決策には
なっていない。この問題クラスへの本命は別のところにある：

- **エラーメッセージへの投資**: 「MCPサーバーが設定されていません」ではなく
  「MCPサーバー'foo'がconfig.ymlに見つかりません。`henji --mcp-list`で確認するか
  config.ymlのmcp-servers:セクションに追加してください」まで書けば、エラー自体が
  「失敗した瞬間に届くドキュメント」になる
- **診断コマンド**（`henji doctor`的なもの）: 「MCPが実際に設定されているか」は
  静的に書けなくても、実行時に検査するコマンドは提供できる。ドキュメント側は
  「実行前に`henji doctor`で確認せよ」と書けば、静的テキストと実行時の
  不確実性を橋渡しできる

### 4.2 発見可能性（discoverability）の検証が必要

エージェントはほぼ確実に`--help`を最初に叩く。新設する詳細ドキュメント機構への
誘導文（例: `For detailed docs: henji docs`）自体が検証対象。誘導文の書き方・位置
（`--help`の冒頭か末尾か）で発見率が変わりうるため、これまでと同じ検証ループ
（opencode/codexにタスクを与える）を、今後は2段階に分けて測定すべき：

- 段階1: エージェントが誘導文に気づき、詳細ドキュメントコマンドを実行するか
- 段階2: その内容でタスクを完遂できるか

段階1と段階2の失敗は原因も対処も異なるため、検証ログで区別して記録する。

### 4.3 分離軸は「人間 vs AI」ではなく「クイックリファレンス vs 詳細マニュアル」

`--ai-description`という命名は「AIしか読まない」という前提を固定してしまう。
実際には詳細な使用例・フラグ間の依存関係・前提条件は人間にも有用であり、これは
伝統的なCLIの`--help`（簡潔）と`man`ページ（詳細）の分離と同型。「AI向け」と
名付けることの実害：

- 人間ユーザーが「自分向けじゃない」と判断し詳細ドキュメントの存在に気づかない
- AIエージェント側も、珍しいフラグ名より`docs`/`manual`/`man`のような見慣れた
  語彙の方が学習分布に乗っており発見・利用しやすい可能性がある

### 4.4 具体的な設計提案

**コマンド名（案A、推奨）**: サブコマンド`henji docs`
```
henji docs           # 全体の詳細ドキュメント
henji docs mcp       # トピック別（将来の拡張、コンテキスト節約にもなる）
```
**案B**: サブコマンドを持たないCLI設計を維持したいなら`--manual`/`--long-help`
（`--ai-description`より汎用的な名前を推奨）

### 4.5 重要な前提条件（Claudeが調査して発見）: 現状の`--help`はサブコマンドを一切表示しない

案Aを採用する場合、実装前に踏まえるべき制約がある。`main.go`の`usageFunc`（`--help`の
出力を生成する自前実装）は、cobraの標準テンプレートが持つ「Available Commands:」
セクション（サブコマンド一覧+1行説明）を出力するロジックを持たない。現に既存の
`completion`サブコマンド（`henji completion bash`等、README記載）ですら`--help`には
一切表示されず、README等の外部情報でしか知りようがない。

つまり`henji docs`をサブコマンドとして追加しても、**`usageFunc`に「Available
Commands:」的なセクションを追加する作業とセットでなければ`--help`には出てこず、
4.2で指摘された発見可能性の問題がそのまま再発する**。案Aを実装する際は、
`usageFunc`の拡張を前提タスクとして計画に含めること。

**ファイル形式**: Markdown。装飾なしのプレーン出力を推奨——ANSIエスケープや
glamourレンダリングはAIエージェントにとってノイズになりうる。

**`--help`との内容重複の管理**: `--help`は「フラグ一覧+1行説明のみ」、
docsは「タスク指向の説明（〜をするには）と落とし穴のみ」として役割を非対称にし、
同じ情報を二箇所に書かない編集規約を決める。

**配置場所・`go:embed`の制約**: `//go:embed`は**パッケージディレクトリ外
（`../`を含むパス）を埋め込めない**。よって`internal/docs/`のようなディレクトリに
`.md`ファイルと埋め込み用`.go`ファイルを同居させるのが、`config_template.yml`と
同じパターンで最もシンプル。

### 4.6 その他の指摘

- **ドキュメントのテスト可能性**: 埋め込んだMarkdown内のコード例（フラグ名等）が
  実在するかを検証するテストを書けば、機能変更でドキュメントが古くなる問題を
  機械的に検出できる（開発者の問題提起4の懸念を`go:embed`とは別の角度からも軽減）
- **「他のAIも同じ提案をしていた」は妥当性の根拠として弱い**: 複数のAIが同じ提案を
  するのは、提案が正しいからではなく同じ学習分布から似た「もっともらしい答え」を
  出しているだけの可能性がある。妥当性の根拠は実測（検証ループでのタスク成功率の
  変化）に置くべきで、AI同士の意見の一致は参考程度に留める
- **バージョン間の互換性表示**: `go:embed`はバイナリとドキュメントの一致を保証するが、
  逆に言えば古いバイナリは古いドキュメントを出し続ける。docs出力の冒頭に
  `henji vX.Y.Z のドキュメント`とバージョンを自動挿入しておくと、エージェントが
  古い情報を掴んだ際の自己診断材料になる（`ldflags`で既にVersion埋め込み済みなので
  低コスト）

## 5. Claudeが実際にhenjiを使ってみて気づいた点

Fable 5へのレビュー依頼（henji経由で実際に対話）で、`--max-tokens`を低い値
（2000→1500→800、本来なら増やすべきところを逆に減らしてしまった）で指定した結果、
長い回答が毎回途中で切れ、`-c <conversation-id>`で3回継続する羽目になった。

これはhenjiのバグではなく実装担当者（Claude）自身の使い方のミスだが、`--help`の
`--max-tokens`の説明（「Maximum number of tokens in response」の1行のみ）には、
「小さすぎると文の途中で切れて`-c`での継続が必要になる」という運用上の注意が
書かれていない。今回の一連の議論（静的ドキュメントの限界、エラー/UXへの投資）と
同じ文脈の実例として記録しておく。
