## 1. `--image`（vision対応）— 実装する

### 設計方針

- 入力は `--image FILE` とstdin（magic byte判定）の両対応
- **アダプター層は新設不要**。`internal/proto` の正規化メッセージ層が既にあり、`proto.Message` のcontentをテキスト単一から content parts（text/image）の列へ拡張する。型付きブロックで定義し、`map[string]any` の組み立ては避ける
- content parts は**メディアタイプ非依存**に設計しておく（将来のPDF・音声追加を安価にするため）
- プロバイダーごとの変換: Anthropic `image`+`source.base64` / OpenAI互換 `image_url`+data URI / Gemini `inline_data`+`mime_type`
- プロバイダーごとの画像サイズ・枚数制限（Anthropicは1枚5MB等）のバリデーションを入れる
- `-f` と同じ「1回1ファイル」ポリシー（下記参照）

### 非対応モデルへのフォールバック方針（重要）

- **既定は明示的な失敗（fail-closed）**。「警告して画像を除外」を既定にすると、モデルが画像を見ないまま自信満々の回答を返す「静かに間違う」故障モードになる。スクリプトから使うフィルターでは最悪
- 劣化を許容したい場合のみ `--drop-unsupported-media` のような明示フラグで
- 「visionエラーをキャッシュして次回フォールバック」は**やらない**。キャッシュは状態であり、同じコマンドが前回と違う動きをするフィルターになる。エラーはその都度明確に返す

### 実装時の注意

- リクエスト組み立てを触るので `scripts/e2e-gateway-test.sh` に画像ケースの追加が必要（[[feedback_e2e_gateway_testing]] 参照）
- セキュリティ面: visionは未信頼入力の面を画像へ広げる（画像内テキストによるprompt injectionは実在する）が、henjiの出力がテキストに留まる限り副作用の境界は変わらず、MCP廃止後の安全モデルを崩さない

## 2. `-f, --file`（テキストファイル添付）— 実装する

### 動機

現状 `henji "指示" xx.txt` は**ファイルを読まない**。`main.go:112` で位置引数はすべて空白結合されプロンプト文字列になるため、モデルには文字列 `指示 xx.txt` が送られる。エラーにならず、モデルがファイル名から内容を推測して回答しかねない（静かに間違う）。

`-f` は多段パイプラインで「原文を各段に再添付する」パターンを成立させる。`--image` の再指定パターンのテキスト版であり、対になる:

```sh
cat xx.txt | henji "指示1" | henji -f xx.txt "指示2" | henji -f xx.txt "指示3"
```

### 仕様（合意済み）

1. **ちょうど1ファイル限定**。pflagの通常のString型は繰り返し指定で黙って後勝ちになるため、**custom Valueで2回目の `-f` を明示的にエラー**にする（数行）。グロブ展開（`-f *.txt` → `-f a.txt b.txt c.txt`）で複数流れ込んでも即発覚する
2. **ファイルっぽい位置引数へのstderr警告**: 位置引数が実在するファイルパスと一致したら `warning: prompt argument "b.txt" is an existing file — did you mean -f b.txt?` を出す。処理は止めない（ファイル名をプロンプトに書く正当なケースがあるため）。グロブ展開ミスと `henji "指示" xx.txt` 誤用の両方をこれ一つで検出できる
3. **バイナリガード**: 先頭数KBにNULバイトがある・UTF-8として不正なら「バイナリに見える。`-f` はテキスト専用」とエラーで止める。放置するとGoのstringには入るが `encoding/json` マーシャル時に不正UTF-8がU+FFFDへ潰され、モデルには置換文字のスープが届く（トークン課金だけ発生して情報ゼロ、`MaxChars` を食い潰して後続プロンプトが切り捨てられる恐れもある）。将来 `--image` 実装後は同じ検査点でmagic byteを見て「PNGなので `--image` では?」と案内する分岐にできる
4. 複数ファイルの一括投入はstdinの仕事: `cat *.txt | henji "指示1"`。パイプ途中で大量再添付したくなったら、事前に1ファイルへ結合するサイン。**henji側でのグロブ自前展開はやらない**（クォート有無で挙動が変わる予測しにくいツールになる）
5. 実装の足がかり: `load.go` の `loadMsg` が `file://`/`https://` 読み込みを持つ（現在はrole設定でのみ使用）。流用すれば `-f` はURLも受けられる（採否は実装時に判断）

### 関連する既知の穴（別途判断）

`cat xx.zip | henji` は現状同じ経路（バイナリ→U+FFFD潰れ）を通る。stdin側にも同様の警告を入れるかは既存挙動の変更になるため別途判断。

## 3. 多段パイプライン — 実装不要、READMEにレシピを文書化

ディベート型・多視点レビュー型のパイプラインはテキストだけなら現状で動く:

```sh
cat 議題.txt | henji "賛成派として意見を" | henji "反対派として反論を" | henji "司会として両論をまとめて"
```

- モデルを段ごとに変えるバリエーションも現状可能
- 実務応用: 設計レビューを賛成/反対/中立で多段検証
- 段数分コストと時間が線形に伸びるため「たまに使う深掘りツール」の位置づけ
- `-f` 実装後は原文再添付パターンが加わり実用性が上がる

## 4. `HENJI_PIPELINE_ID`（セッション伝播）— 継続検討

「環境変数があれば同一会話として扱う」案。既存SQLite会話履歴の流用可能性と、環境変数がなければ完全に従来動作という低侵襲性は魅力。ただし**未解決の罠が2つ**あり、解が出るまで着手しない:

1. **コミット順序の保証**: パイプラインの各段は並行に起動する。順序が保たれるのは「後段はstdinを読み切るまでAPIを呼べない」からで、前段が**stdoutを閉じる前に会話をSQLiteへコミットする**保証がないと、後段の見る履歴がタイミング依存になる。「数行のロジック」ではなくこれが実装の本体。また `xargs -P` 併用時は同一IDへの競合書き込みになるため「直列パイプ専用・並列実行と併用禁止」の明文化が必須
2. **コンテキストの二重化**: 後段は前段の出力をstdinと会話履歴の両方で見る。「履歴があればstdin無視」は解にならない（stdinを読み切ることが実行順序の同期機構そのものだから）。読み捨てて履歴だけ使うか、重複を許容するか、決める必要がある

## 5. JSONペイロード（画像込みエンベロープ）— 保留

- 当初案（`--json-schema` で画像込みJSONを出力）は**そのままでは成立しない**: json-schemaは構造化「出力」なので、モデルが数MBのbase64を出力トークンとして再生成することになる。課金が莫大・base64は忠実に複製できず画像は破損・途中で切れる、の三重の破綻
- 成立させるなら、henji自身が入力画像を出力エンベロープへ詰め直す**パススルー機構**（`--emit-envelope` 等の別フラグ）として設計し直す必要がある
- しかし元画像はほとんどの場合ディスク上に残っており、`--image` の各段再指定で用が足りる。エンベロープが勝つのは「画像がファイルとして存在しないケース」だが、henjiは画像を出力しないので当面存在しない
- **visionを使い込んで「`--image` 再指定で足りない実例」が出るまで保留**

## 6. `--voice` / `--mov` — 見送り

1. プロバイダー対応が画像よりまだら（Anthropic APIは音声・動画入力非対応。OpenAI互換も音声は特定モデル限定）。henjiの主戦場では大半のバックエンドでエラーになる
2. Unixフィルター的代替が成熟: 音声は `whisper-cpp audio.wav | henji "要約して"`、動画は `ffmpeg -i clip.mov -vf fps=1 frame_%d.png` → `--image`。「音声→テキスト」「動画→静止画」は独立フィルターであり、curlへの委譲と同じパターン。READMEにレシピとして記載する
3. 動画のbase64ペイロードは巨大でパイプ設計と相性が悪い

proto content partsをメディア非依存にしておけば、状況が変われば追加は安価。優先度では音声・動画より**PDF**が先（Anthropic公式対応、「論文PDFを要約」はユースケースど真ん中）。
