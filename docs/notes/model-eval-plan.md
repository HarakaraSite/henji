# モデル別 henji 利用能力テスト計画

作成日: 2026-07-04  
確定日: 2026-07-04（権限モード・ゲートウェイ・タイミングをユーザー確認済み）  
目的: 背景知識ゼロの AI セッションが `henji -h` と `henji docs` だけを頼りに henji を
使いこなせるかをモデル別に測る。結果は v2.0.0 基準(「AI が自律実行時に henji を能動的に
発見・選択・実行するに足る」)の判断材料、および -h / docs の改善入力にする。

## 対象（ドライバー）モデル — 3セッション

| セッション | モデル | 起動コマンド |
|---|---|---|
| A | Opus 4.8 | `claude --model opus --dangerously-skip-permissions` |
| B | Sonnet 5 | `claude --model claude-sonnet-5 --dangerously-skip-permissions` |
| C | Haiku 4.5 | `claude --model haiku --dangerously-skip-permissions` |

権限は skip-permissions で無人実行（ユーザー確認済み。/tmp 配下の隔離ディレクトリ）。

## ゲートウェイ側（henji が叩く）モデル — 2種を両方テスト

| 呼称 | モデル | 経路 |
|---|---|---|
| local | mlx-community/gemma-4-E2B-it-qat-4bit | localhost:8080（vmlx-engine） |
| cloud | gpt-5.5 | api.openai.com（api-key-cmd で Keychain から取得） |

各ドライバーセッションは**両方のゲートウェイモデルで同じタスクを実施**する。
評価用 config には2モデルを設定しておくだけで、どちらがどれか・切り替え方法の発見
（`--list-models`・`-m`/`-a`）自体もテスト対象になる。
gpt-5.5 は reasoning モデルのため `max-completion-tokens: 4096` をモデル設定に入れる
（本番 henji.yml と同じ理由: 未設定だと thinking で消費され空応答になる）。

## テスト環境（背景情報の遮断）

- 作業ディレクトリは **mods リポジトリの外**: `/tmp/henji-eval/<session>/`。
  リポジトリ内で起動するとプロジェクト CLAUDE.md・自動メモリ（henji の知識だらけ）が
  読み込まれるため。ユーザーグローバル CLAUDE.md のみ残るが henji には無関係。
- `henji` は **--help 簡素化コミット（`3eb221f`）後のビルド** を使用（確認済み）。
- 各ディレクトリの `./henji` は `XDG_CONFIG_HOME` を自分の `xdg-config/` に向ける
  ラッパースクリプト（テスト対象に env 指定の負担を負わせない）。実体は `bin/henji-bin`。
- `cache-path` も各ディレクトリ内 `data/` に向け、ユーザー本来の設定・会話DBに触れない。
- 配布物: `INSTRUCTIONS.md`・`access.log`（合成ログ約60行、404スキャン・500バースト等の
  異常を含む）・`sample.go`（SQLインジェクション・リソースリーク・無保護の並行マップ書き込み
  を仕込んだ約60行）。3ディレクトリとも同一内容。

## タスク設計

**タスク1（基本）— パイプ入力と出力の取り出し**
`access.log` を要約させ、要約テキストだけをファイルに保存。
測るもの: 基本の起動形、パイプ、装飾・メタ情報を混ぜない出力の取り出し。

**タスク2（応用）— 構造化出力と会話継続**
`sample.go` をレビューさせ (1) 指定 JSON 形式で保存、(2) **同じ会話の続き**で1件深掘り。
測るもの: `--json-schema` / `--output json` への到達、conversation_id の発見と `-c` 継続。
docs を読まないとまず解けない難易度。

タスク文には**フラグ名・機能名を一切書かない**（発見できるか自体が測定対象）。
成果物はゲートウェイモデルごとにサフィックス `.local` / `.cloud` で分ける。

## 評価軸（RESULT.md テンプレートで統一）

1. タスク成否（ローカルモデルの応答品質による失敗は「コマンド組み立ては正しかったか」で分離）
2. 試行コマンド数と失敗の内訳（存在しないフラグの捏造があったか）
3. 情報源の使い方: `-h` だけで足りたか、`docs` をいつ・なぜ読んだか
4. エラーからの回復力（local の schema リトライ多発時の挙動を含む）
5. henji への改善提案 — v2.0 判断と -h/docs 改善の直接入力

## 実行手順

1. ✅ 簡素化後ビルドの確認（test/vet パス、--help 一覧性確認済み）
2. `/tmp/henji-eval/{opus,sonnet,haiku}/` を構築
3. herdr で新規タブを作り、セッションA（Opus）から**逐次**実行
   （ゲートウェイが単一のため。並列だと応答遅延が混入し比較が歪む）
4. 各セッションへの投入プロンプトは全モデル共通:
   「カレントディレクトリの INSTRUCTIONS.md を読んで、その指示に従ってテストを実施してください。」
5. 完了ごとに RESULT.md を回収し、次のセッションを起動
6. 3件回収後、`docs/notes/model-eval-results-2026-07.md` に比較表として集約

## INSTRUCTIONS.md（配布する指示文・全セッション共通）

```markdown
# henji 利用能力テスト

このディレクトリで CLI ツール `henji` を使い、以下の2つのタスクを完了してください。
`henji` は `./henji` として実行できます（設定済み）。

henji には**2つのモデルが設定されています**: ローカルの軽量モデルと、クラウドの
高性能モデルです。どのモデルが設定されているか・どう使い分けるかを調べる方法も、
下記ルールの範囲で henji 自身から見つけてください。

## ルール

- henji に関する情報源は次の3つだけ: `./henji -h` の出力、`./henji docs` の出力、
  実際に henji コマンドを実行した結果。
- 禁止事項: henji のソースコードや README を探して読むこと、Web 検索、
  類似ツールの記憶からフラグを推測して -h / docs で確認せずに使うこと。
- `xdg-config/` 内の設定ファイルは変更・閲覧しないでください（設定ファイルを読めば
  答えが分かってしまうため。モデル一覧の確認も henji のコマンドで行うこと）。
- 試したコマンドは**失敗したものも含めてすべて** RESULT.md に記録してください。
- 各タスク×各モデルの目安は10分です。超える場合は「未完了」として状況を記録し、
  次に進んでください。全体で45分を上限とします。

## タスク1（基本）

`access.log` の内容を henji に要約させ、要約テキスト**だけ**を保存してください。
（スピナー・進捗表示・装飾・JSON の外皮などが混ざっていないこと）

- ローカルモデルで実施 → `task1-summary.local.txt`
- クラウドモデルで実施 → `task1-summary.cloud.txt`

## タスク2（応用）

`sample.go` を henji にレビューさせ、2段階で成果物を作ってください。
ローカルモデルとクラウドモデルのそれぞれで一連の流れを実施します。

**ステップ1**: 指摘事項を機械可読な構造化データとして受け取り、次の形式の JSON で
保存する:

    {"findings": [{"title": "...", "severity": "high|medium|low", "line": 0}]}

- ローカル → `task2-findings.local.json` / クラウド → `task2-findings.cloud.json`

**ステップ2**: 指摘のうち1件を選び、**ステップ1と同じ会話の続きとして**（新しい会話では
なく、henji が文脈を覚えている状態で）修正方法の詳しい説明を求め、回答を保存する:

- ローカル → `task2-detail.local.txt` / クラウド → `task2-detail.cloud.txt`

完了条件: findings が上記形式の有効な JSON であること、detail がステップ1の指摘を
踏まえた続きの回答になっていること。
```
