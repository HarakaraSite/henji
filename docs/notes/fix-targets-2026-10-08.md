## 保存失敗による既存の会話本文の削除

対象: [main.go](../../main.go) の `saveConversation`（584〜589行）、
[internal/cache/cache.go](../../internal/cache/cache.go) の `Cache.Write`。

`saveConversation` は同じ ID の `.gob` を上書きしてから SQLite の索引を更新する。
索引の更新に失敗すると、後処理の `cache.Delete(id)` が継続元の本文まで削除する。

再現条件と結果:

1. 隔離した設定・履歴ディレクトリとローカル模擬 API で、新規会話を保存する。
2. 同じ ID を `--continue` で継続する。
3. 模擬 API が応答を返す直前に、別の SQLite 接続で `BEGIN EXCLUSIVE` を実行し、保存までロックを保持する。
4. henji は保存失敗で終了コード `1` を返し、既存の `.gob` を削除する。ロック解除後も索引の行は残る。

一時テストでも、既存の会話に対して `PRAGMA query_only=ON` で索引更新を失敗させ、同じ削除を確認した。

修正方針: 既存本文を直接上書き・削除する手順を見直し、本文と索引の更新に失敗しても
継続元の本文・索引を保持する。新規保存の後処理と、既存会話の更新失敗を区別する。

受入条件: 索引更新が失敗しても元の会話を表示・継続できる。正常な継続では新しいターンを保存できる。

### 2026年10月8日の対応

本文を同じ `conversations/` ディレクトリ内の `.henji-cache-*` へ書き、同期・close が成功してから
置き換える。元の本文も一時ファイルに退避し、索引更新が失敗した場合は元の本文を戻す。
新規保存の失敗では新しい本文だけを削除する。復元自体が失敗した場合は退避ファイルを保持し、
その場所と復元エラーを通知する。一時ファイルの権限は `0600`。

同じ会話は、履歴読込から生成・保存・復元まで OS のファイルロックで排他する。
後続要求は先の保存後に更新済みの履歴を読む。別会話は並行実行でき、ロック待ちは context の取消で終了する。
分岐では読込先と保存先を ID 順にロックし、表示・削除も同じロックに従う。
ロックファイルは `conversations/.locks/<id>.lock` に置く。待機中のプロセスが同じファイルを
ロックする必要があるため、ロックファイルは終了時に削除せず、ハンドルを閉じて排他だけ解除する。

並行起動時に SQLite の初期化が `SQLITE_BUSY` で失敗することも確認した。
全接続に最大5秒の競合待機を設定し、初回のテーブル・列作成を一つの即時トランザクションで直列化した。
これにより初回の同時起動でも列追加が競合しない。

確認: 新規・継続の正常保存、索引更新失敗時の本文・索引の保持、途中で失敗する本文書込の保護、
複数プロセスでの同一会話の順次継続と別会話の並行完了、ロック待機の取消、
SQLite の同時初期化と短い書込競合からの再開を回帰テストで確認した。

## エラー処理中の stdin 待機

対象: [main.go](../../main.go) の `handleError`（404〜409行）。

`handleError` はエラーを表示する前に `io.ReadAll(os.Stdin)` で入力を読み切る。
上流がパイプを閉じなければ、エラー表示と終了が EOF 待ちで止まる。この読み込みは
ルート context の取消を参照しない。

再現条件と結果:

- 子プロセスの stdin をパイプにし、書き込み側を開いたまま `henji --invalid-review-flag` を起動する。
- 不正なフラグが確定していても終了しない。
- 書き込み側を開いたまま henji プロセスだけに `SIGINT` を送っても終了しない。

修正方針: エラー時に stdin を読み切る必要性を見直し、上流の EOF に依存せず
診断を出して終了できるようにする。読込を残す場合も取消を反映する。

受入条件: 上流が入力を閉じなくても不正なフラグで速やかにエラー終了し、終了処理が取消を妨げない。

### 2026年10月8日の対応

`handleError` から stdin を読み切る処理を削除した。書き込み側を開いたままのパイプを渡しても、
フラグのエラーを stderr に表示して終了することを、子プロセスの回帰テストで確認した。

## JSON モードのエラー出力の不統一

対象: [main.go](../../main.go) の root command `RunE`（122〜125行、156〜192行）と `handleError`。

JSON エラー出力は主に `mods.run()` が `modsError` を返す経路に限られる。
その前後の失敗は同じ形式で出力されない。また、成功 JSON を保存処理より先に出力するため、
後から保存に失敗しても stdout に `error` が反映されない。

再現条件と結果:

- `henji --output json --json-schema /存在しないファイル "prompt"` は終了コード `1`、stdout は空、診断は stderr のみ。
- 上記の会話継続時の SQLite ロックでは、終了コード `1` にもかかわらず、stdout は応答本文を含む `error` のない JSON。

修正方針: JSON モードのエラー出力を一か所で管理し、要求準備・生成・保存の各段階の失敗を
一行の envelope に反映する。保存失敗時も生成済みの応答を利用できるよう、本文を残したまま
エラーを伝える。成功出力とエラー出力を二重に出さない。

受入条件: スキーマ読込失敗と保存失敗のどちらも、有効な一行 JSON と非ゼロ終了コードを返し、
`error` に失敗理由が入る。成功時の既存 envelope との互換性を維持する。

### 2026年10月8日の対応

JSON エラーの出力を共通の `handleError` にまとめ、通常の error と `modsError` の両方を扱う。
要求処理は生成済みの応答をエラーと一緒に引き渡し、成功 JSON は保存成功後に出す。
これによりスキーマ読込・入力準備・生成・保存の失敗でも一つの envelope を出し、保存失敗時は
`content` と `error` が共存する。JSON の version と既存フィールドは維持した。
DB 初期化はフラグ解析後に行い、初期化の失敗も選択済みの出力形式で通知する。
設定読込はフラグ解析前のため、出力形式をまだ選べない設定読込失敗は stderr に通知する。

確認: 子プロセスの CLI テストで正常応答、no-cache、スキーマ・添付読込失敗、入力不足、
モデル不明、フラグ不正、DB 初期化失敗、API 認証失敗、継続の保存失敗を確認した。
JSON は一つだけで、保存失敗でも生成済みの応答と元の履歴本文が残る。

## 入力の切り詰めによる UTF-8 の破損

対象: [stream.go](../../stream.go) の `setupStreamContext`（60〜61行）、
`inputPartsForContent`、`limitTextParts`。再試行時の `cutPrompt` も同じ観点で確認する。

`max-input-chars` の比較と切り詰めは、文字数ではなく Go の文字列のバイト数・バイト位置を使う。
日本語などの複数バイト文字を途中で切ると、不正な UTF-8 が要求メッセージに入る。

再現条件と結果: `setupStreamContext("あい", Model{MaxChars: 4})` で、メッセージ本文は
`e3 81 82 e3` になり、`utf8.ValidString` が `false` を返した。

修正方針: 切り詰めを UTF-8 の文字境界で行う。上限をバイト数とするか文字数とするかは、
既存設定への影響を考慮して決め、マニュアルの単位と実装を一致させる。

受入条件: 通常入力・添付テキスト・再試行の切り詰めで UTF-8 を壊さず、選んだ単位の上限を守る。

### 2026年10月8日の対応

既存設定との互換性を保つため `max-input-chars` のバイト上限を維持し、UTF-8 の文字境界まで
戻して切り詰める。通常入力、添付テキスト、再試行の短縮で同じ処理を使う。
複数のテキスト部分間の区切りも結合プロンプトの上限に数え、画像と添付の非保存属性は保持する。
設定名は維持し、ヘルプ・README・組込マニュアルに単位を記載した。

確認: 日本語・絵文字・引数との結合、no-limit と未設定上限、添付と画像の順序、
再試行の短縮をテストし、有効な UTF-8、元入力の接頭辞、バイト上限内であることを確認した。

## キー取得コマンドの stderr 混入

対象: [mods.go](../../mods.go) の `ensureKey`（574〜583行）。

`api-key-cmd` を `CombinedOutput()` で実行し、stdout と stderr の合計を API キーとして使う。
取得コマンドが正しいキーを stdout に返しても、stderr に警告があればキーに混ざる。
この動作は [Go の CombinedOutput の仕様](https://pkg.go.dev/os/exec#Cmd.CombinedOutput) と一致する。

再現条件と結果: 次の設定値を `ensureKey` に渡すと、返るキーは `fake-keydiagnostic` になった。

```yaml
api-key-cmd: sh -c 'printf fake-key; printf diagnostic >&2'
```

修正方針: stdout をキーとして取得し、stderr は分離する。コマンド失敗時のエラー終了と、
既存のキー優先順位は維持する。診断を出す場合、キー本文を表示しない。

受入条件: stdout がキー、stderr が診断でもキーは正しく取得できる。コマンドの非ゼロ終了はエラーとして扱う。

### 2026年10月8日の対応

`CombinedOutput()` を `Output()` に変更し、stdout だけを trim してキーとする。
stderr は分離してキーに含めない。失敗時のエラー終了と、空の stdout なら下位のキーを使う
既存の優先順位を維持した。空白だけのコマンド設定は、panic せず設定エラーにする。
キー本文やコマンドの出力を診断に追加しない。

確認: キーを stdout・診断を stderr に出す成功、空の stdout での fallback、
キーを stdout に出した後の非 0 終了、空白コマンドを回帰テストで確認した。
